## 요약

GPT의 핵심 지적 세 가지에 동의합니다.
1. 점수 공식보다 **데이터의 시점과 정확성**이 먼저다.
2. 무료 API 사용과 **완전한 백테스트 데이터 확보**는 별개 문제다.
3. 가중치만 고정해서는 과최적화를 막을 수 없다. 업종·필터·유니버스·결측 규칙도 전략의 일부다.

이에 따라 개발 순서를 **"데이터 확보 검증 → 계산 검증 → 최소 백테스트 → 검증 통과 기능만 화면 노출"** 의 게이트 방식으로 바꿨습니다 (DESIGN 10장).

이견은 세 가지입니다.
- 1-1: 과거 최초 공시 값의 완전 복원
- 2-1: 업종 자동 상향 전면 금지
- 6-1: 백테스트 선행 순서

세부 내용은 아래 표에 정리했습니다.

## 이견 상세

### ① 과거 최초 공시 값의 완전 복원 (1-1 관련)

**동의하는 부분**
- `rcept_no`, `available_at`, `collected_at`, 정정 연결, `source_hash` 저장은 필요합니다.
- 체결가 가정을 명시해야 한다는 점도 맞습니다.

**이견**
- 무료 API로 **과거의 최초 공시 버전을 전부 복원할 수 있는지는 확인되지 않았습니다.**
  - `fnlttSinglAcntAll`이 정정 후 값을 주는지, 최초 값을 주는지 아직 확인하지 못했습니다.
  - 접수번호별 원본(XBRL) 파일 경로가 대안이지만, 전 종목·전 기간 적용은 비용이 큽니다.
- 이것을 착수 조건으로 삼으면 프로젝트가 막힐 수 있습니다.

**조치**
- **앞으로 수집하는 데이터**: 수집 시점부터 완전한 시점 관리(PIT)를 보장합니다.
- **과거 데이터**: 0단계에서 최초 값 복원 가능 여부를 검증합니다.
  - 불가하면 정정 후 값으로 백테스트하고, 결과에 "정정 반영값 사용" 한계를 표시합니다.
  - 정정공시 빈도를 측정해 영향 규모를 추정합니다.

### ② 업종 자동 상향 (2-1 관련)

**동의하는 부분**
- 종목 수만 보고 실행할 때마다 자동으로 묶으면 업종 동질성이 훼손됩니다.
- 그렇게 하면 시점마다 비교 집단이 달라져 재현성도 떨어집니다.

**이견**
- 상향을 아예 하지 않으면 3~5개 종목짜리 업종의 백분위가 의미를 잃습니다.
  - 예: 4개 중 1위 = 100점

**조치**
- **사전에 고정한 "비교 사업군" 표**를 사용합니다.
  - KSIC를 사람이 검토해 묶은 표이며, 버전으로 관리합니다.
  - 실행 중에 종목 수를 보고 자동 병합하지 않습니다.
- 표본이 10개 미만인 사업군은 점수 신뢰도를 "낮음"으로 표시합니다.
- 다음 세 방식은 실험으로 비교합니다: 사업군 표 vs KSIC 원분류 vs 전체 시장.

### ③ 백테스트 순서 (6-1 관련)

**동의하는 부분**
- 실전 추적만으로는 검증이 되지 않습니다.
- 데이터 확보 가능성은 먼저 검증해야 합니다.

**조정**
- 0단계에서 과거 데이터 확보 가능성을 검증합니다.
  - 과거 일자별 시세, 상장폐지 이력, 기업행위, 정정 이력
- 2단계에서 계산 검증을 통과한 엔진으로 최소 백테스트와 실전 추적을 **병행**합니다.
- 화면 노출은 그 이후입니다.

GPT 제안과 사실상 같은 방향입니다. 다만 **"계산 검증 전 백테스트 금지"** 를 추가했습니다. 계산이 틀린 엔진으로 돌린 백테스트는 오히려 해롭기 때문입니다.

### D-11 히스토리 저장 (부분 수정)

GPT 지적대로, 상위 100개만으로는 백테스트를 대체할 수 없습니다.

- 정규화 데이터 계층(DuckDB/Parquet)에 **전 종목 일별 점수를 압축 저장**합니다.
- 화면용 JSON에는 상위 종목만 내보냅니다.
